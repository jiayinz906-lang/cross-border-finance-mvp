# 灾难恢复 Runbook

## 恢复目标

- 建议 RPO：24 小时以内；月结和大批量导入前增加即时备份。
- 建议 RTO：4 小时以内，具体以服务器、归档大小和审批流程实测为准。

## 场景与处理

### 应用容器故障

1. 开启维护模式并保存日志。
2. 检查磁盘、内存、镜像和健康接口。
3. 重新启动相同 Git SHA；无效时执行应用回滚。
4. 不恢复数据库。

### PostgreSQL 故障

1. 停止业务写入，保护 `/data/xjd-finance/postgres`。
2. 复制故障数据目录和日志用于分析。
3. 在全新空库恢复最近通过校验的归档。
4. 比较 manifest，完成业务抽样后再切换连接。

### CVM 或数据盘故障

1. 新建满足安全基线的 CVM 和独立数据盘。
2. 从 Git 的批准版本重建应用，不复制未知容器状态。
3. 从私有 COS 下载备份并校验 SHA-256。
4. 恢复数据库、证书和环境变量，完成验收后切换 DNS。

### 凭据泄露

1. 立即撤销相关 CAM、COS、数据库、SSH 和应用密钥。
2. 轮换 `AUTH_TOKEN_SECRET` 后，所有旧 token 自动失效。
3. 审计登录、导入、下载、签名和数据导出记录。
4. 必要时封禁来源 IP，并按企业流程通知负责人。

## 演练

每季度至少完成一次“COS 下载、SHA 校验、空库恢复、manifest 对比、只读验收”全流程演练。演练记录包括用时、RPO/RTO、失败点、负责人和整改截止日期。

## 关键原则

- 数据恢复与应用回滚分开审批。
- 不在原正式库上做覆盖式恢复。
- 没有实际恢复验证的备份不视为可用备份。
- 事故未调查清楚前不删除日志、归档、容器元数据或故障数据盘快照。
