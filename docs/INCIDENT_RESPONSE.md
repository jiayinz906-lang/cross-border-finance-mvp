# 生产事故响应

## 分级

- **P0**：数据丢失、金额错误扩散、凭据泄露、系统全面不可用。
- **P1**：核心导入/签名/收付款不可用、持续 5xx、严重性能下降。
- **P2**：局部页面、单一角色或非核心导出异常。

## 前 15 分钟

1. 指定事故负责人和记录人，建立时间线。
2. 对可能继续写坏数据的故障立即开启维护模式。
3. 保存应用、Nginx、数据库、系统和审计日志。
4. 确认影响月份、账号、订单、确认单和接口范围。
5. 不删除容器、数据卷、备份或故障现场。

## 遏制与诊断

```bash
bash ./scripts/maintenance-on.sh
bash ./scripts/tencent-status.sh
docker compose --env-file .env.tencent -f docker-compose.tencent.yml logs --since=2h backend nginx postgres
```

检查最近发布 SHA、数据库迁移、维护状态、磁盘、内存、连接数、5xx 和审计日志。涉及金额时导出当前 manifest，与最近已知正确 manifest 比较。

## 恢复决策

- 仅应用代码异常：回滚到批准的 Git SHA。
- 数据库异常：保持维护模式，先备份故障库，再恢复到新空库并验收。
- 凭据泄露：撤销并轮换所有相关凭据，强制旧 token 失效。
- 任何数据库恢复均需双人审批，不由发布脚本自动执行。

## 恢复后

1. 验证健康接口、登录、月份、Dashboard、金额、文件和签名。
2. 观察错误率、P95、数据库连接和备份至少一个业务高峰。
3. 通知业务恢复，并记录尚未解决的问题。
4. 48 小时内完成复盘：根因、影响、时间线、处置、改进项和负责人。

## 联系与证据

正式上线前在企业内部维护联系人表，不写入公开仓库。事故证据至少包括 Git SHA、镜像 ID、环境版本、数据库迁移、日志时间范围、备份 SHA 和处理命令。
